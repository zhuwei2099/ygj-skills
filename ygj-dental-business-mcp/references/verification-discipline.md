# 验证与举证纪律

**什么时候读**：准备下「取不到」「不存在」「全 0」「没有这个字段」这类**否定结论**之前，或要把一条实测结论写进技能 / 交付给用户之前。

本服务端有多处「看起来是接口属性、实际只是当时样本」的坑。下面 4 条是实测踩坑换来的，**下否定结论前逐条过一遍**。

> ℹ️ 下文案例中出现的 `appoints_list` 是该接口的**旧名**，2026-10-15 起更名为 **`clinics_list_appoints`**，旧名已于 2026-11-13 **从本技能移除**（服务端 `tools/list` 仍有残留，**不得使用**）。案例保留当时的原始记录**不做改写**；引用其字段口径时按**新名**调接口。

## 1. 「取不到数 / 全 0」是时刻属性，不是接口属性

- **案例（2026-09-28）**：当日上午跨 6 家真实门店 **38 次调用全部 `total=0`** → 据此判定 `appoints_list`「不可用」并让病历质量报告降级走患者维度；**同日 16:0x 再调，全部有数**（逸康 57 / 龙岗 61 / 宝安 39 / 岳麓 26 / 望城 7），同时 `employees_list` 也从「跨 20+ 家全 0」变成 **宝安 83 人** —— 服务端在当天下午完成了数据接入。
- **规则**：任何「全 0 / 取不到数据」的结论，**写进技能或交付时必须带核对时刻**；**再次引用前必须重新实测 1 次**（1 次调用、约 3 秒）。
- 跨店一致为空只能证明「**此刻**该域无数据」，**不能写成永久属性**。
- 降级路径（fallback）本身没错，但**降级前要先重测**，别把 3 秒的成本省成一次错误结论。

## 2. 「schema 声明」≠「运行时返回」

- **出参字段数**以**实际返回的键**为准，不要用 schema 的 `properties` 计数。`appoints_list` schema 声明 **81**、运行时只返回 **71**（`assistantId` / `nurseId` / `roomId` / `scheduleId` / `consultantId` / `onlineConsultantId` / `preceptorDoctorId` / `consultantGroupId` / `originAppointId` / `isKnowItem` 共 10 个不返回）。
- **入参字段不一定在返回体里**：`appoints_list` 的 `isReach` 是**查询入参**，**记录里没有该字段** → 判「是否到店」只能用 **`reachTime` 非空**。凡是「看到入参名就以为出参也有」的推断，都要实拉一次验证。
- 🚨 **「键缺席」≠「字段不存在」—— 服务端会省略取值为 `null` 的字段键**（2026-10-13 实测：某店 `bill_docs` 500 行，`combId` / `mainItemId` 各缺 480 行、`consultantId` 缺 487 行；**全表没有 `null` 值，只有「键不在」**；空字符串 `""` 则保留）→ 同一接口不同样本的字段数会差很多（实测 `bill_docs` 出现过 **65 / 69 / 71 / 74** 四种）。

## 3. 存在性三步法（判「某字段 / 某项数据有没有」）

- **上位原则（举证责任倒置）**：凡「**不存在 / 取不到 / 全 0**」的结论，**举证责任都在结论提出方** —— 必须拿出「**该字段该有值的场景下也没有**」的证据。拿不出，就只能写「**本次样本未出现，未验证**」，**不得升级为接口属性**（与第 1 条同源）。
- **三步法**：
  1. **看声明** —— 该字段在 `outputSchema` 里有没有（声明有即可否定「根本没这个字段」，但**声明有 ≠ 每行都有**）；
  2. **看运行时** —— 实际返回的键（注意服务端**按行省略取值为 `null` 的键**，见第 2 条）；
  3. **找对照样本** —— 换一个「该字段**应有值**」的样本复测（判 `combId` 就用**有组合行的门店**，别拿没组合的店下结论）。
- **判定三分（写报告必须标类别）**：

  | 类别 | 情形 | 结论 |
  | --- | --- | --- |
  | **A** | 声明有 + 运行时出现 | ✅ 存在 |
  | **B** | 声明有 + 运行时未出现 | ⚠️ **未验证**（**禁止写成「不存在」**） |
  | **C** | 未声明 + 运行时出现 | 🔎 服务端扩展字段（`additionalProperties:true`，**以运行时为准**） |

- **报告纪律**：字段数一律写「**本样本出现 N 个字段**」，**不写「接口 N 字段」**。
- 历史探针脚本 `$SKILL/scripts/ygj_field_probe.py`（一条命令输出「主样本 vs 对照样本」字段差集 + 三分类判定 + null 省略检测 + 键缺失分布）**未随本技能分发**（见 [changelog.md](changelog.md) §三），需要时从备份取回或按本节重写。

## 4. 官方文档给的是「口径」，不是「事实」

- **上位原则**：文档 / 甲方的每一句**关于数据本身的断言**（字段有值、几个字段、是否一一映射、几类取值、是否相等）都是**待验证命题**，不是结论。**可实测就必须实测**；测不了才退回「照录并标注未验证」。
- **实测例（2026-10-13）**：官方文档称「`oaOrgId` 与 `clinicId` 一一映射」→ 复测 **288 行 = 281 个 `oaOrgId`，7 个各挂 2 个 `clinicId`**，**且文档后文自己举了「深圳宝安 = 2 个 clinicId」的反例** → 属**文档内部自相矛盾**，**以实测为准**（本技能已按 **1:N** 定稿，见 [clinic-and-staff-lookup.md](clinic-and-staff-lookup.md)）。
- **写进技能的正确姿势**：**官方口径原文照录**（那是权威），**紧随其后附「✅ 本机实测（时间）」**；两者冲突时**保留两者 + 明确标注以实测为准**，并写清**影响面**（例：改按 `oaOrgId` 汇总会改变「深湾店 / 宝安店」既有数值）→ **不得为了「忠于文档」而把实测证据删掉**。
- **配套检查**：凡文档给出的**结构化枚举**（几类、几档、几个字段），一律**先实测一遍再写「共 N 类」**（同日已出现：`itemTypeMasterName` 实 6 类非 4 类、`itemTypeSubName` 至少 15 种、补牙档位并集 12 档）。

## 5. 与统计口径的关系

- 第 2、3 条是报表口径的前提：数量 / 金额聚合依赖 `combId` / `mainItemId` / `labelLevel1` 是否存在 —— **字段存在性判错，整套统计跟着错**。参见 [label-level-rules.md](label-level-rules.md)、[combo-transaction-by-patient.md](combo-transaction-by-patient.md)。
- 第 1 条适用于所有「这个接口是不是没数据」的判断。
