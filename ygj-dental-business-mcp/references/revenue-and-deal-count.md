# 收入口径与成交人数口径

涉及**金额统计**或**成交 / 体检人数**时读本文件。日常明细查询不需要。

## 一、支付分类与金额两口径

### 支付分类取值范围

| 值 | 含义 |
| --- | --- |
| `0` | 现金类实收 |
| `1` | 预收款使用 |
| `2` | 支付优惠 |
| `3` | 平台结算 |
| `4` | 其他代收 |

### 支付分类与金额口径对应规则（严格遵循，避免混淆或错误归类）

| 口径 | 支付分类范围 | 说明 |
| --- | --- | --- |
| **营业额** | `0`-现金类实收、`3`-平台结算 | 门店实际流水收入（**不含**预收款使用） |
| **交易实收** | `0`-现金类实收、`1`-预收款使用、`3`-平台结算 | 含预收款核销的交易实际收款 |

> ⚠️ 两口径差异**仅在是否包含 `1`-预收款使用**：营业额不含、交易实收含。统计前先确认目标口径，再按对应支付分类过滤求和，不得混用。

## 二、取数接口规则（收入相关场景）

- **适用范围**：**所有与收入相关的数据获取场景**（营业额、交易实收、业绩金额、收费收入等）一律遵循本规则。
- **一律仅使用交易接口**取数：
  - 门店维度 → **`clinics_list_bill_docs`**（按交易时间 `optDateTime` 归集，`sum(payAmount)` 即净实收，退费已以负数行计入）；
  - 患者维度 → **`patients_list_bill_docs`**（按交易明细归集，同样取 `payAmount`）。
- **不使用账单接口**：门店 **`clinics_list_bills`**、患者 **`patients_list_bills`** 在收入相关场景**一律禁用**。
- 收入统计口径按「支付分类与金额口径对应规则」过滤求和：营业额 = 支付分类 ∈ {0,3}；交易实收 = 支付分类 ∈ {0,1,3}。

## 三、体检与成交人数统计口径（核验必读）

**口径 1：体检收费判断规则**

- **原口径（双侧）**：账单 `isPhysical` = `1` **且** 交易 `isPhysical` = `1`，**同时满足两者**才判定为**体检收费**；输入字段：账单 `isPhysical`、交易 `isPhysical`。
- **落地口径（单侧，收入相关场景）**：体检收费属**收入相关场景** ⇒ 按铁律 9「收入只走交易接口」，**账单接口不得调用**，账单侧 `isPhysical` 取不到 → **改为只用交易明细侧 `isPhysical` = `1` 判定**。
  - 实测样本：某店当日明细侧 `isPhysical`=1 共 20 行、`payAmount` 合计 11,840.00，与双侧取交结果**逐分一致**（该样本单侧 = 双侧），并与当日体检登记名单 9 人实收吻合。
  - ⚠️ **该样本单侧 = 双侧属巧合性一致**（原双侧结论的依据就是「仅账单 = 1 另有 18 单」）⇒ 单侧判定在**其它样本仍可能偏差**；出数时**必须标注「明细侧单侧判定，未与账单侧交叉验证」**。
- **非收入场景**（如纯体检登记名单核对）若要双侧，须说明理由，且仍不得为了取账单侧数据而破坏铁律 9。

**口径 2：员工离职状态判断规则**

- 判断条件：`oaJobStatus` = `离职`
- 计算规则：满足 → 判定为**离职状态**
- 统计用途：区分在职 / 离职员工（如员工清单、业绩归属核验时按需排除或单独统计离职员工）
- 输入字段：员工 `oaJobStatus`

**口径 3：医生体检成交人数判断规则**

- 判断条件：消费金额 > `0` **且** 支付分类 ∈ {`0`-现金类实收, `3`-平台结算} **且** 交易状态 = 正常 **且** `isPhysical` = `1`（是）
- 计算规则：满足条件后，**先按 `doctorId` + `doctorName` 汇总**，**再按 `patientId` 去重**计数 → 各医生的体检成交人数
- 输入字段：`doctorId`、`doctorName`、`patientId`、消费金额、支付分类、交易状态、`isPhysical`

**口径 4：体检成交人数判断规则**

- 判断条件：消费金额 > `0` **且** 支付分类 ∈ {`0`-现金类实收, `3`-平台结算} **且** 交易状态 = 正常 **且** `isPhysical` = `1`（是）
- 计算规则：满足条件后，**按 `patientId` 去重**计数 → 门店 / 全院体检成交人数
- 输入字段：`patientId`、消费金额、支付分类、交易状态、`isPhysical`

**口径 5：成交人数判断规则**

- 判断条件：消费金额 > `0` **且** 支付分类 ∈ {`0`-现金类实收, `3`-平台结算} **且** 交易状态 = 正常
- 计算规则：满足条件后，**按 `patientId` 去重**计数 → 门店 / 全院成交人数
- 输入字段：`patientId`、消费金额、支付分类、交易状态

> 口径 3/4/5 关系：**5** 为通用成交人数；**4** 在 5 基础上**额外要求** `isPhysical`=1（限定体检）；**3** 在 4 基础上**额外按医生维度**（`doctorId`+`doctorName`）分组汇总。统计核验时按目标口径选择，不得混用。

## 五、分部 / 大区级业绩出数流程（2026-10-15 定；要出「某分部/负责人 的门店业绩」时按此）

**六步，顺序不可换：**

1. **取分部所有门店** —— `employees_list_work_clinic` **一次调用**（行数以当次返回为准；2026-10 样本 288 行），按 `divisionalGeneralManager == 负责人` 筛出 `clinicId` 集合；同名负责人可能挂多个 `divisionalId`，需先判元素个数（见 [clinic-and-staff-lookup.md](clinic-and-staff-lookup.md) §四）。**不需要、也不得调用员工表 `employees_list`**。
2. **取交易记录** —— 对名册内每个 `clinicId` 调 `clinics_list_bill_docs`（`startDate`/`endDate` + `current`/`size` 翻页；单店单次，**无多店批量入参**）。
3. **按交易门店归店** —— 🚨 返回体里门店字段是 **`optClinicId`**（交易门店），**不是**请求入参的 `clinicId`。归店必须用 `optClinicId`；`optClinicId` 不属于本分部门店集合的行**剔除**，并在报告里透明列示剔除行数与金额。时间轴为返回体 **`optDateTime`**（交易时间，非入参）。
4. **按组织机构聚合** —— 门店(`optClinicId`) → **`oaOrgId`**（同组织多门店合并）→ 分部合计 = Σ 各组织机构。
5. **行级归集两道工序**（顺序不可换）：
   - ① **整行精确去重**（整行指纹）—— 多店查询可能重复取到同一行；
   - ② **同 `(billId, billDetailId)` 多行判定**（🚨 实测有两种形态，**必须分开处理**）：
     - **互补阶段行**（金额与数量落在**互斥位置**，如开单行 `refundCount=n/payAmount=0` ＋ 收款行 `payAmount=x/refundCount=0`，时间相差数秒）→ **必须按字段求和合并**，合并后才是完整一行；合并行的归期取 `max(optDateTime)`。
     - **反向冲销对**（收 `+x/+n` ＋ 退 `−x/−n`，两个位置都非零）→ **禁止合并**，按两笔独立事件入账 —— 合并会把退费抵消成 0、**掩盖退费事实**。
     - 两种口径下 `SUM(payAmount)` 与 `SUM(refundCount)` **完全相同**，差异只在「行数 / 收费额 / 退费额 / 退费行数」。
6. **出报表** —— **每个分部负责人一个独立 HTML**（不要合并到一个 HTML 里）。

**指标**：净实收 `SUM(payAmount)`；收费额 `SUM(payAmount>0)`；退费额 `SUM(payAmount<0)`；营业额 `SUM(payments[].payAmount, payType∈{0,3})`；数量 `SUM(refundCount)`；成交客户 = 口径 5（`patientId` 去重）—— 同时给「分部作用域去重」与「各店分别去重后求和」两个数（后者同一客户跨店会重复计）。

**必做勾稽**（任一不成立即不得出数）：原始行 − 精确去重 − 互补合并 = 归店后行数 = 保留行数 + 跨店剔除 + 时间越界剔除；Σ门店 = Σ组织 = 分部合计（行数与净实收）；净实收 = 收费额 + 退费额；**Σpayments 分型之和 + `payments` 为空行的净额 = 净实收**（见 §六 的 R6 订正）。

## 六、全门店营业额排名（2026-11-01 定；要出「各门店营业额排名 / 体检与非体检拆分」时按此）

数据源与 §五 完全相同（`employees_list_work_clinic` 1 次取**账号授权范围内**的全量名册 —— ⚠️ **授权范围 ≠ 全公司门店，见下方硬约束 4** → 逐店 `clinics_list_bill_docs` → `optClinicId` 归店 → `optDateTime` 定期间），差别只在「范围是全部门店」与「多一个体检维度」。

**口径**

| 指标 | 定义 |
| --- | --- |
| 营业额 | `SUM(payments[].payAmount, payType ∈ {0,3})`（现金类实收 + 平台结算；不含 1/2/4） |
| 体检收入 | `isPhysical = 1` 的行，**按上面同一口径**求和 |
| 非体检收入 | `isPhysical = 0` 的行，同口径求和 |
| 门店粒度 | 按 **`oaOrgId`** 合并（同组织多门店并一行）；也可按 `clinicId` 逐店 |
| 上榜条件 | 该期间**有交易明细行**的组织（含营业额为负/为 0 的退费店） |

**三条硬约束（都是实测踩出来的）**

1. 🚨 **R6 恒等式必须加一项**：`Σpay_by_type == 净实收` 在**月度全量**下**不平**（2026-10 全公司差 39,114.00）。原因是有 `payments` **为空数组**的行（实测 15 行 / 0.016%，全部为 `billType=1`、`feeType=3`「项目抵扣」的负数行），其 `payAmount` 进了净实收但不落任何 `payType`。正确判据：**`Σpay_by_type + Σ(payments为空行的 payAmount) == 净实收`**。§五 的同类勾稽同样按此修正。
2. 🚨 **`isPhysical` 缺键率远高于经验值**：2026-10 全量 91,923 行中有 **2,293 行（1.5%）** 整个键缺失（不是 0），金额 771,091.30。处理：先按 `billId` **同单众数回填**（本次仅救回 2 行），仍回填不到的并入「非体检」**并单独披露行数与金额**。⇒ 体检占比存在**向下偏差**，出数必须注明。
3. 🚨 **「体检收入」是客户来源口径，不是项目口径**：`isPhysical=1` 表示这次收费属于**体检来源客户**的整单，实测其项目构成约 85% 是补牙/牙周/修复等治疗项目。报表必须写明，避免被读成「体检套餐卖了多少钱」。

4. 🚨🚨 **名册 = 「账号被授权的门店」，不是全公司门店**（2026-11-01 血案）：`employees_list_work_clinic` 无参调用返回的是**当前 API 账号门店数据授权范围**内的门店。同一账号在**补授权前后**分别返回 **288 家 / 308 家**；10 月全公司营业额随之从 50,870,855.46 → **53,096,699.46**（差 **2,225,844.00**，全部来自新增 20 家中 7 家有交易的门店）。**接口不报错、不告警，R1–R10 勾稽全 PASS** ⇒ 纯内部校验**发现不了**，只能外部对账。
   - **三道防线（缺一不可）**：① 出数后与财务/BI 的期间总额**对一次账**，差异 > 0.5% 立即停查；② 报表**固化打印「在册门店数 / 组织数」+ 核对时刻**，让范围可复核；③ 授权变更后**整批重跑**（缓存按 `clinicId` 分文件 ⇒ 老店命中、新店自动拉取，一次跑完即完成合并）。
   - **实测锚点**：补授权新增 20 家（16 家「新开待开业」但**当月已有交易**，勿按状态剔行），7 家有交易合计 **2,225,844.00** —— 武汉平安好医 417,512.00 / 玉林慈铭 258,876.00 / 沈阳阳光铁西 312,117.00 / 石家庄美年美华桥西口腔 137,178.00 / 成都美年高新 628,504.00 / 上海美宏 384,036.00 / 郑州豫慈 87,621.00。

**其它**：`isPhysical` 为**行级字段**（number 0/1，schema 有定义）；互补阶段行合并时取首行标记，需加一致性检查（实测同单内 100% 一致，冲突率极低）；门店简称 `abbreviation` 会重名且有脏值，**join/去重只用 `clinicId` / `oaOrgId`**。报表另有「**状态**」列（`clinicStatus` 原值，脏值原样输出不猜测）：它是**当前在册状态**、**不是「本月是否营业」** —— 取数**不按状态剔行**（2026-10 实测 182 家有交易门店中：营业中 170 / **新开待开业 9** / 暂停营业 2 / **已撤店 1**）；同组织多店状态不一致时显示「混合」，不得取首店代表。
